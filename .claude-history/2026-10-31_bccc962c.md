## 合っているところ

- **効果は決まった部品の組み合わせだけで作る。** 破壊・バウンス・ドロー・ダメージ・無効などの部品をエディタで組み合わせてカードを作ります。部品にない効果は作れません。
- **足りない効果は開発側が部品を足す。** `企画書.md` にも「ブロックを追加するとき、開発者＋AI」が証明する、と書いてあります。表せないもの（フェイズ・プレイヤーを対象にする効果・禁止の効果など）は `進捗.md` の残課題に並んでいます。
- **ルールを上書きする部品は、わざと用意していない。** 検査で弾くのではなく、そもそも組み立てられないようにしています（`企画書.md` 144行目）。

## 違うところ：証明は「有限だから全部調べる」方式ではない

ほとんどの証明は、盤面を総当たりしていません。**「どの部品をどう組み合わせても、1手ごとに制約が守られる」ことを、部品ごとに一度だけ証明します。** その結果、どのカードを作っても、どれだけ長い対戦でも成り立ちます。カードの枚数が何枚でも、盤面がどれだけ広くても通る作りです。

有限であることを使っているのは、次の2か所だけです。

- **カードの一覧で決まる★**（ライフや攻撃力の上限など）：そのゲームのカード一覧から値を計算し、それが上限だと証明する
- **無効の関係に循環があるとき**：小さな盤面（1人2枚まで・合計5枚まで）だけを総当たりする

## 部品を足すときの注意

- 部品を1つ足すと、1手の定義（`Step` など）が広がります。そのため、既存の定理をすべて証明し直すことになります。部品が増えるほど組み合わせの場合分けも増え、少しずつ重くなります。
- 凍結した主張（`spec/`）は、この定義を使っています。定義を広げると、主張の文面が同じでも意味が変わるので、人が差分を見る必要があります。
- 「自然言語で書いた効果を部品の組み合わせに変換する」部分は、まだありません。今はユーザーが自分でエディタの部品を組み合わせる形です。

まとめると、「部品の語彙を足していく」方式なのは合っています。ただ、証明は総当たりではなく「部品ごとに一度だけ証明すれば、どんな組み合わせでも成り立つ」形です。

凍結した主張って何？

## Claude（2026-11-01 11:43）

例を見せるために、凍結した主張のファイルを確認します。

凍結した主張とは、**「何を証明したと言っていいか」を人が決めて書き写し、AI が変えられないようにした文面**のことです。ファイルは `spec/Spec/Statements.lean` にあります。

## なぜ必要か

AI に証明を書かせると、次のような形で「通ったこと」にされるおそれがあります。

- 証明しにくい命題を、こっそり弱い命題や自明な命題にすり替える
- 仮定を足して、何も言っていない定理にする
- `sorry` や勝手に足した公理で、証明を飛ばす

Lean のビルドが通っても、**「何を証明したか」が元のままかどうかは、ビルドだけでは分かりません。** そこで、主張の正解を別のファイルに固定し、照合するようにしています。

## 例

「各プレイヤーのカードは、名前ごとの枚数が開始時のデッキのまま」という★は、`Statements.lean` に次のように書いてあります。

```lean
def cards_perm : Prop :=
  ∀ {r : Rules} {decks : PlayerId → List Card} {g : State}, Reachable r decks g →
    ∀ (p : PlayerId), (g p).cards.Perm (decks p)
```

読み方：どのルール・どのデッキでも、到達できる盤面なら、各プレイヤーのカードは開始時のデッキの並べ替えになっている。

`spec/Spec/Check.lean` は、CardGen 側で証明した定理をこの文面に当てはめます。

```lean
theorem cards_perm : Spec.cards_perm := @CardGen.Reachable.cards_perm
#assert_std_axioms Spec.Checked.cards_perm
```

CardGen 側の定理の型が凍結した文面と少しでも違えば、ここでビルドが失敗します。2行目は、使っている公理が標準の3つだけかを確かめます。

## 守り方

- `spec/` は Claude Code から書き換えられないようにしてあります（`.claude/settings.json`）。変えるのは人だけです。
- `spec/check.sh` がこの照合をまとめて行います。ソースの禁止語の検査や、カーネルでの再検査もします。
- このゲートは、コミット前・CI・Claude が作業を終える時に毎回走ります。
- 今は、レポートが「証明済み」と出す 23 本の定理がすべてここで照合されています。

## 穴

文面に出てくる `Reachable`（到達できる盤面）や `Step`（1手）の定義は、CardGen 側にあって凍結していません。たとえば `Step` を「何もしない」に変えれば、文面は同じでも中身のない主張になります。

前の話で「部品を足すと主張の意味が変わる」と言ったのはこのことです。そのため、定義を変えたときは、何を変えたかを書いて人が見る決まりにしています。

## Claude（2026-11-01 11:46）

ほぼその通りです。数学と同じように、証明を積み上げて定理を作っています。ただ、2点だけ補足します。

## 1. 中心にあるのは「数学的帰納法」

ほとんどの★は、次の2段で証明しています。

1. **始まりの盤面で成り立つ。** たとえば、開始時のカードはデッキそのもの。
2. **成り立っている盤面から1手進めても、また成り立つ。** 破壊でもドローでも戦闘でも同じ。

この2つから、「何手進めても成り立つ」が言えます。対戦の長さは無限にありえますが、示すのはこの2つだけで済みます。

## 2. 条件分岐はちゃんと全部たどっている。ただし具体的な値ではない

ここはテストと少し似ています。2段目の「1手」の証明では、**1手の種類（部品）ごとに場合分けして、すべての分岐を確かめます。** 1つでも漏れると Lean が通しません。

テストとの違いは、各分岐を**記号のまま**扱うところです。

| | テスト | 証明 |
|---|---|---|
| 調べるもの | 「攻撃力 1500 のカードを破壊」など具体的な1件 | 「どんなカード・どんな盤面で破壊しても」 |
| 1回で確かめる範囲 | 1件 | その分岐に入る無限通りすべて |
| 分岐の漏れ | 気づかないことがある | 漏れると通らない |

ですから「条件分岐を全部網羅する」のは合っています。ただし、値は総当たりせず、記号のまま全部を一度に扱っています。

## 「公理から」「矛盾しない範囲で」について

- **公理**は、Lean の土台の論理と標準の3つ（`propext`・`Classical.choice`・`Quot.sound`）だけです。ゲームのルールは公理ではなく**定義**として書いています。ルールを公理として足すと、矛盾したルールから何でも証明できてしまうからです。
- **矛盾しないか**を確かめているわけではありません。ルールの定義が決まったうえで、「その定義なら、この性質が必ず成り立つ」を示しています。

一言でいうと、「ルールを定義として書き、その定義から数学的帰納法で性質を証明している。場合分けは全部たどるが、値は記号のまま」という作りです。
